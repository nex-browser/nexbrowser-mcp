# NexCaptcha tasks and page workflow

## Choose the integration workflow

Keep the user's browser session. Prefer the agent-driven flow below when its permitted tools can read the current HTML and apply a result. Every paid task, price, team context, record and refund still belongs to NexCaptcha. Read the selected product's online `integration.workflows`, result contract and `workflowGuide`; availability and an implemented application path are separate requirements. The optional `workflow` argument on `nex_captcha_buy` declares the intended integration and is checked before charging; it does not grant browser capabilities.

| Workflow              | Choose only when                                                                                                                                                                                                                                                    | Current MCP boundary                                                                                                                                                                                                                                                                          |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `HTTP_SUBMIT`         | The online contract permits it and an established site integration can obtain actual challenge inputs, preserve the required session and submit both verification and business requests over HTTP. Prefer this route when those conditions are already established. | `nex_captcha_product_list` → `nex_captcha_product_schema` → `nex_captcha_buy` → `nex_captcha_query` supplies recognition. Target-site HTTP submission, session handling and acceptance checks need a separate site integration; this is not a generic website HTTP runner.                    |
| `BROWSER_RESULT`      | Real challenge inputs and a permitted way to apply the native result in the original page/frame.                                                                                                                                                                    | Prefer agent HTML detection → NexCaptcha buy/query → generated token application for reCAPTCHA v2/enterprise or Turnstile. Other products require an explicit integration or the optional fixed Desktop bridge.                                                                               |
| `BROWSER_INTERACTION` | A real image-grid challenge matches the online GRID contract and Desktop can capture its original image/instructions and execute its required clicks.                                                                                                               | The same browser tools use GRID capture/native clicks, with visible reCAPTCHA grid detection or observed selectors for other regular grids. Arbitrary rotation, dragging, canvas and irregular puzzles are not implemented by this bridge. Both MCP and Desktop need the Grid implementation. |

The fixed Desktop route `nex_browser_captcha_prepare` → `nex_browser_captcha_submit` → `nex_browser_captcha_complete` is optional. A missing initialization capture limits that route, not an agent integration with real parameters and a permitted application path. Neither route is an automatic three-way router or a generic HTTP integration.

HTTP 403, timeouts or invalid/missing parameters do not justify switching to GRID, stripping a required challenge value or ignoring the online contract. Report missing product, input or execution capability concretely. Select Grid only from a real supported current image challenge. Never spend to discover missing parameters, use examples as real inputs or bypass disabled browser permissions.

Check three outcomes separately: recognition succeeded (`SUCCEEDED`), the target accepted verification, and the intended business operation completed. `applied=true` only describes local result application; it does not prove the last two outcomes. Grid `websiteVerified=true` requires an explicit configured acceptance signal and still does not establish business completion.

## Agent-driven browser flow

1. Keep the original browser session, page and frame. Confirm that the agent's existing browser tools can read the current HTML and execute the supported result application. `nex_browser_evaluate` and `nex_browser_run_code` retain their existing permissions. If disabled, use a supported fixed bridge or report the execution limitation before paying; do not evade policy with raw CDP or shell/browser scripts. Never silently reload a filled form.
2. Read HTML from that actual page/frame and call free `nex_captcha_detect({url, html, canApply: true})`. Set `canApply=true` only after establishing permitted read/application capability; it defaults to false. Initial detection supports reCAPTCHA v2/enterprise and Turnstile. The tool returns observed candidates, the online contract and precise readiness/conflicts; it neither solves nor purchases. Optional `productCode` and `adapter` must come from current page evidence, not guesses. Explicitly select the intended widget when several exist.
3. `ready=true` supplies validated purchase arguments, not proof of website acceptance. Read the complete online contract and detection warnings. For Enterprise, unsupported optional `s` is omitted with a warning and does not block this flow. Other unsupported observations and missing schema-required inputs remain blockers; do not borrow another provider's parameter name. HTML cannot reveal all runtime-only parameters; do not claim automatic support for other products, Cookie application or hCaptcha.
4. For the authorized task, call the returned `nex_captcha_buy` arguments, including `workflow: "BROWSER_RESULT"`, once. This remains the only paid task-creation tool for this path and uses the current NexCaptcha server price. Save the returned local `id`, not upstream `taskId`. A price/availability inquiry alone must not buy.
5. Poll `nex_captcha_query(id)` every 3–5 seconds only while pending. Stop on `SUCCEEDED`, `FAILED` or `EXPIRED`; never repeat task creation to poll. Unknown purchases require `nex_captcha_record_list` and `nex_billing_trade_list` reconciliation before any new charge. Failed/expired refunds remain server-managed.
6. For a supported successful token task bought in this MCP process, call free `nex_captcha_apply_result({id, url, websiteKey, selector?})`. Keep the same page URL/site key used for purchase. An optional selector must identify an observed unique widget container. The tool queries the existing local task and returns `apply.javascript`; it neither creates a task nor executes code. Recheck the original page/frame and challenge, then execute through an already permitted browser tool and inspect the site's response. Generated code does not click a final login/signup button.
7. After MCP restart, the saved application binding is unavailable. Query/reconcile the existing task and use an explicit supported integration; do not buy again to restore a binding. If script execution throws or its outcome is unclear, inspect the page before replay or repurchase. A generated script or local application result does not establish website acceptance.

For other products, use their exact online schema plus an explicit agent integration, or the fixed Desktop bridge. Online availability alone does not implement application. Local image matching is not a substitute for NexCaptcha recognition.

## Standalone product parameters

Product rules come exclusively from the online `POST /nex_captcha_schema` endpoint through the signed-in Desktop client. `nex_captcha_product_schema(productCode=selectedCode)` is free and read-only, requires a connection, and returns the complete `productCode`, `schema`, `example`, `integration`, `workflowGuide` and any future fields. There is no bundled product catalog, fixed product count, lookup alias, or offline fallback. The server caches schemas for one hour by product and language; prices have a separate ten-minute cache.

The purchase tool uses the flat `productCode` and `adapter` arguments. Its public tool schema checks common input shape and platform-key protection. Before buying, it reads and validates against the current online product schema, including `oneOf`, types and `additionalProperties`. The complete online result is also available as JSON text for hosts that consume only `content`.

The upstream [2Captcha reCAPTCHA v2 Enterprise contract](https://2captcha.com/api-docs/recaptcha-v2-enterprise) accepts `enterprisePayload`, including an observed `s` value. Its [standard v2 contract](https://2captcha.com/api-docs/recaptcha-v2) names that input `recaptchaDataSValue`, which some Google challenges require. These upstream names do not automatically expand the NexCaptcha wrapper contract. For Enterprise, `enterprisePayload.s` is optional: detection forwards observed `s` when the online schema supports it, otherwise omits it with a warning and permits a task without it. Omission does not guarantee website acceptance. Missing schema-required inputs still block purchase; never force undeclared fields or change products to evade validation.

1. Read `nex_captcha_product_list` for enabled products and payable single-task USDT prices. Keep the exact product code, including case; do not rewrite or trim it.
2. Call `nex_captcha_product_schema(productCode=selectedCode)`. Read the complete schema, `integration.resultSchema/resultGuide` and `workflowGuide`. Examples contain placeholders; replace them with actual authorized challenge inputs. Do not invent values, borrow another product's fields or submit platform API keys.
3. Stop before purchasing if the online schema cannot be read or validated, the result contract is incomplete, or readiness is `DOCUMENTATION_REQUIRED`. Never substitute old documentation or start a paid task to discover missing rules. Product-specific validation follows the online schema and the backend/upstream, with no local product definitions.
4. Call `nex_captcha_buy(productCode, adapter)` once for the requested task. The server charges the current price directly, without a quotation stage or separate payment confirmation. A price inquiry alone must not create a paid task. Desktop manages authentication and balance; do not request a NexCaptcha API key.
5. Retain the local `id` and query `nex_captcha_query(id=localId)`, never upstream `taskId`. Poll only as needed at 3–5 second intervals. Stop polling on SUCCEEDED, FAILED or EXPIRED; CREATED, SUBMITTING and PROCESSING are pending. Interpret the solution using the online product contract. Unknown purchases, purchase/application timeouts and restarts require reconciliation through `nex_captcha_record_list` and `nex_billing_trade_list`; stop new charges while unknown. Confirmed FAILED/EXPIRED or explicit site rejection permits a genuinely new challenge within 3 attempts including the first, without another confirmation. FAILED/EXPIRED refunds are server-managed; verify billing.

Online product availability does not imply automatic browser capture or completion. Browser tasks additionally require a supported online browser workflow and an actual application path, using the agent-driven flow above or the optional fixed bridge below.

## Optional fixed Desktop bridge

When a CAPTCHA blocks a user-authorized browser flow, check NexCaptcha first. Keep the original sessionId and pageId explicit throughout. Solve necessary CAPTCHAs directly unless the user restricted paid tools.

When using nexbrowser-mcp for browser tasks, use a NexBrowser environment by default. Reuse the selected environment or call `nex_browser_list` and `nex_browser_connect(windowId, startIfNeeded=true)`. This fixed route captures/applies widgets without arbitrary evaluation permission. A failed preparation does not rule out the agent-driven route when real inputs and permitted execution are available; parameter/schema conflicts still block payment on both routes.

An explicit registration/login request authorizes its normal final submit and necessary CAPTCHA solving unless the user has restricted it. Submit prepared challenges directly without a quotation stage or payment confirmation. Re-preparation returns a new prepareId tied to the current challenge; retain it for submit and complete.

1. Call `nex_browser_captcha_prepare(sessionId, pageId)`. It reads enabled products before inspecting the page, then checks the selected online contract and BROWSER_RESULT support (BROWSER_INTERACTION for GRID). Preparation is free. The result either supplies a short-lived prepareId or explains the missing product, parameters or callback. With multiple widgets, explicitly choose a returned challengeId. Never guess between widgets.
2. Prefer preparing before navigation; NexBrowser navigation/reload installs the bridge before page scripts initialize. Updated Desktop can also recover existing/implicit reCAPTCHA only when it can associate the callback. Enterprise requires the exact enabled `RECAPTCHA_V2_ENTERPRISE` online contract and updated MCP. Recovery does not reload or re-render the page. `ready=false` limits this fixed route; an agent may use the general route only with validated real inputs and permitted application. GeeTest and Turnstile fixed adapters still depend on captured initialization. Explain blockers before any approved reload; do not lose filled inputs or assume reloading fixes a contract conflict.
3. For GeeTest v3, do not submit the challenge already loaded into the widget. Identify the same-origin GET request that fetched the original `gt` and `challenge` using `nex_browser_network_requests` (and its recorded response). Pass its exact observed URL as challengeUrl in prepare. Submit fetches a fresh matching challenge before purchase. Endpoints that require POST, additional headers, JSONP or a different response shape need a site-specific adapter; never guess or replay arbitrary requests.
4. Use the prepared challenge only for the requested task and honor user restrictions. Price and availability inquiries alone must stop before submission.
5. Call `nex_browser_captcha_submit(prepareId)` directly. It rechecks product availability, user/team context and page challenge, charges once at the server price, and retains the local task ID. Never substitute the upstream taskId. A failed/unknown response may follow a debit; keep the prepareId and reconcile `nex_captcha_record_list` and `nex_billing_trade_list`. Stop new charges while the outcome is unresolved. State is local to this MCP process: after a restart, reconcile before any new purchase.
6. Call `nex_browser_captcha_complete(prepareId)` to query once and dispatch a successful answer to the captured widget. Pending results return a retry interval; wait 3–5 seconds before another call and stop when no longer needed. It never starts background polling or purchases. Confirmed FAILED/EXPIRED returns RETRY_CHALLENGE: inspect records/billing, refresh through the widget's supported controls and prepare a genuinely new challenge, then submit directly without asking again, at most 3 attempts including the first. Re-preparing the same attempted challenge remains blocked. Unknown states/network errors do not prove failure or a refund; unknown application blocks repurchase even if the widget changes.
7. Read a fresh page snapshot and, when needed, the site's verification response. `applied=true` means the original callback received the answer; `websiteVerified=false` deliberately makes no acceptance claim. The callback may itself send verification requests or submit a site form as part of the requested flow; honor user restrictions on those effects. These tools do not click a final login/signup button. A callback that throws may already have sent the request: inspect the site, never dispatch it again automatically.

Navigation, resets, expiry, frame changes and locally observed account/team changes block reuse of old tasks. Solutions stay between the service and original page, outside workflow results. A CAPTCHA success does not authorize device approval, ambiguous recovery codes or unsupported SMS challenges.

Hand over only after reporting a concrete blocker on the available routes: unavailable product, missing/expired parameters, unsupported contract, missing execution capability, a user restriction or rejected site verification. Do not stop solely because a CAPTCHA appeared or a fixed callback was not captured.

Product parameter and result contracts follow the [official NexCaptcha documentation](https://app.nexcaptcha.net/openapi/docs.cgi?lang=zh-CN). Browser integration details also reference the [GeeTest v3 browser API](https://docs.geetest.com/captcha/apirefer/api/web).

## Grid browser interaction

Update both the MCP package and Desktop client: the image capture and native clicks run in Desktop's fixed CAPTCHA actions, without arbitrary evaluation permissions. `prepare` detects visible reCAPTCHA image grids even when their token callback was not captured. If multiple token widgets or grids are returned, select the actual Grid `challengeId` explicitly. This is not an automatic fallback from a failed token task.

For another regular image grid, pass observed DOM selectors in `grid` to `nex_browser_captcha_prepare`:

```json
{
  "sessionId": "CURRENT_SESSION",
  "pageId": "CURRENT_PAGE",
  "grid": {
    "root": "#challenge-grid",
    "tiles": ".tile",
    "instruction": "#challenge-instructions",
    "verify": "#challenge-verify",
    "success": "#challenge-accepted",
    "mode": "dynamic"
  }
}
```

`root` must contain only the visible rectangular image grid. `tiles` is relative to that root; the other selectors are scoped to its frame. Instructions and CAPTCHA verification control must each match one visible element. `success` is optional and must identify a visible, explicit acceptance signal, never a generic page container or a business submit control. Regular grids need at least two rows and two columns, at most 100 tiles, at most 1000px per side and a JPEG under 600kB. Images must be loaded, have a regular spatial layout and fit inside an iframe's viewport. `<img>` and CSS background images are supported; canvas, irregular puzzles and unsupported widget behavior need a site adapter. The adapter sends `body` and the unchanged `comment`. It adds observed `rows`/`columns` and `canNoAnswer=1` only when those properties are explicitly declared by the current online GRID schema and the complete enhanced adapter passes that schema; incompatible optional enhancements are omitted. A body/comment-only contract remains supported. It never assumes the backend supports undeclared 2Captcha options or sends `imgType` for screenshots. Dynamic challenges require the service to support a no-match answer; if that is unavailable, report the service contract limitation rather than repeatedly buying replacement grids.

- `static`: click the returned tiles, then the CAPTCHA verification control.
- `dynamic`: click returned tiles and wait for replacements. If replacement is delayed, call `complete` again to inspect without repeating clicks. A later empty `solution.click` means there are no matching tiles and triggers CAPTCHA verify.
- `auto` (default): observed reCAPTCHA dynamic markers, replacement-tile images, or a `replaceimage` request from the current iframe mark the grid as dynamic. That classification is retained while the same root exists. Wait until every clicked tile's original image has been replaced, even if its selection style has already disappeared; call `complete` again when still waiting. Without a known dynamic signal, wait up to three seconds for replacements before deciding whether to verify. Use `dynamic` explicitly for dynamic widgets without recognized signals and `static` for fixed selection challenges.

For the requested task, `submit` charges the current single-round price directly and sends the captured image/instructions. `complete` validates unique 1-based, row-major indexes, binds the answer to the original document/frame/image and checks the remaining targets before each native click. It never clicks a final login/signup button. The image payload and answer stay outside public MCP workflow results.

`complete` returns `gridState`: `WAITING_IMAGES` requires another progress call; `NEXT_ROUND` includes `nextPrepareId` and `nextPreparation` when the current image is ready. Preparation is free: call `submit` directly with that new prepareId when needed, then `complete`. No new paid task is created by `complete`. `REJECTED` identifies a visible reCAPTCHA rejection signal: stop automatic purchases and inspect the site verification response; no next preparation is supplied. `VERIFY_REQUIRED` also requires inspecting the site's verification response; disappearance or an unchanged rejected grid is not proof of acceptance and is not automatically repurchased. `ACCEPTED`/`websiteVerified=true` requires the configured explicit success signal. Without one, verify acceptance from the site separately.

An unknown purchase or partial/unknown click outcome stops replay and repurchase; reconcile tasks/billing and inspect the page. Do not bypass a blocked adapter with raw purchases or local image solving.
